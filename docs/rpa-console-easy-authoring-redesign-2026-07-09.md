## 1. 배경

파일럿 사용자 테스트에서 "어렵다"는 피드백이 확인되었다. 선행 설계(Workato-inspired guided journey)는 기존 구조 최소 수정을 전제로 했으나, 제품 오너가 **재설계 수준 변경을 허용**했다. 본 문서는 그 전제 아래 시나리오 제작 경험을 처음부터 다시 설계한다.

단, 다음은 재설계 대상이 아니라 **지켜야 할 제품 불변식**이다 (§8):
조용한 green 금지, SecretRef 비노출, 백엔드 RBAC 권위, 세션 캡처의 "운영자 PC 등록" 프레이밍, 생성 IR의 codegen ajv + V1–V13 통과.

## 2. 왜 어려운가 — 근본 원인 5가지

실제 코드 기준 진단:

| # | 원인 | 근거 |
|---|---|---|
| 1 | **제작이 패널 더미 속에 있다.** 스튜디오 한 화면에 생성기+브라우저 녹화+수동 폼+승격 인박스+자동화 목록이 세로로 쌓여 있어, 처음 온 사용자는 "어디가 시작인지"를 스크롤로 찾아야 한다. | `web/src/views/Scenarios.tsx:48-168` |
| 2 | **준비물이 선행 조건이고, 다른 화면에 있다.** 사이트 등록·세션 등록은 "보안" 뷰(`#security?section=sites`)에 있다. 업무 사용자는 자동화를 만들려고 "보안"을 열 생각을 하지 못한다. 준비가 안 된 채 실행하면 차단 안내를 받고 화면을 떠나야 한다. | `web/src/views/Security.tsx`, `ReadinessCard.tsx:103-118` |
| 3 | **어휘가 전문가용이다.** SecretRef, IR, 검증 단계, 준비도, 증빙, 멱등성 — 업무 사용자 기준 외국어다. | 전 화면 |
| 4 | **테스트가 화면을 튕긴다.** 실행 버튼을 누르면 `runTrace`로 이동한다. 만들던 맥락이 끊기고, 실행 기록 화면은 운영자용 밀도라 결과 해석이 어렵다. | `RunScenarioButton.tsx:125` |
| 5 | **내비게이션이 18개 뷰 × 3그룹이다.** 업무 사용자에게 필요한 것은 4개 미만인데 전부 보인다. | `web/src/router.ts:29-33` |

공통 패턴: **기능은 다 있는데, 사용자가 시스템의 구조(사이트→세션→시나리오→실행→증빙)를 먼저 학습해야 쓸 수 있다.** 재설계의 본질은 이 학습 부담을 시스템 쪽으로 옮기는 것이다.

## 3. 재설계 원칙

1. **말이 먼저, 설정은 나중에.** 사용자는 업무를 말로 설명하는 것으로 시작한다. 사이트·세션 같은 준비물은 시스템이 필요해진 시점에 그 자리에서 물어본다(just-in-time setup). 사용자를 다른 화면으로 보내지 않는다.
2. **한 화면에서 끝낸다.** 설명→준비→초안→테스트→확인이 하나의 플로우 화면 안에서 완결된다. 화면 이동은 실패가 아니라 선택(상세 증빙 보기 등)일 때만.
3. **사람의 말로 보여준다.** 초안은 "1. 하이웍스에 로그인합니다" 같은 단계 카드로 보여준다. IR/JSON/기술 상세는 "고급 보기" 뒤로 숨긴다. 단, 숨기는 것이지 왜곡하지 않는다 — 상태 어휘(준비됨/확인 필요/보류/차단)는 그대로 노출한다.
4. **역할이 화면을 정한다.** 업무 사용자는 "만들기 콘솔"(단순), 운영자/관리자/보안은 기존 "관리 콘솔"(밀도)을 본다. 하나의 콘솔이 두 밀도를 동시에 만족하려던 것이 지금의 복잡함이다.
5. **불변식은 재설계 대상이 아니다.** §8의 보안·계약 불변식은 쉬운 화면 뒤에서도 그대로 강제된다.

## 4. 목표 경험 — "3분 원패스" 스토리보드

처음 쓰는 업무 사용자 기준, 목표 시나리오:

```
[만들기 홈]
  "어떤 업무를 자동화하고 싶으세요?"  ← 화면 중앙, 큰 입력 하나
  입력: "매일 아침 하이웍스에서 새 결재 문서를 확인해서 목록을 뽑아줘"
  → [자동화 만들기] 클릭

[준비 확인 — 같은 화면, 자동]
  ✔ 대상 사이트: 하이웍스 (자동 인식)
  ⚠ 로그인 연결이 아직 없어요
     → [지금 연결하기]  ← 인라인으로 운영자 PC 등록 가이드 펼쳐짐, 화면 이동 없음
  완료되면 자동으로 다음 단계로.

[초안 미리보기 — 같은 화면]
  1. 하이웍스에 로그인합니다
  2. 결재 대기 목록을 엽니다
  3. 새 문서 제목·기안자·날짜를 읽습니다
  4. 결과를 표로 정리합니다
  ← 각 카드에 아이콘+한 줄 설명. [단계 고치기]는 말로: "3번에서 금액도 같이 읽어줘"

[테스트 — 같은 화면]
  [한 번 실행해 보기] → 단계 카드가 실시간으로 진행 표시(대기→실행 중→성공)
  ✔ 테스트 성공! 4단계가 처리되었습니다.
  → [이대로 사용하기(운영 예약)]  [실행 증거 보기]  [계속 고치기]
```

핵심 반전: 현재는 사용자가 시스템의 순서(사이트→세션→생성→실행)를 알아야 하지만, 목표 경험에서는 **시스템이 사용자의 말에서 순서를 역산해 필요한 것만 물어본다.**

## 5. 새 정보 구조 — 두 개의 밀도

### 5.1 만들기 콘솔 (업무 사용자 기본)

새 뷰 `create` (신규 라우트 — 재설계 허용에 따라 신설). `scenario.create` 권한이 있는 사용자의 기본 진입 화면.

내비게이션 (업무 사용자에게 보이는 전부):

| 항목 | 내용 |
|---|---|
| 만들기 | `create` — 만들기 홈 + 원패스 위저드 |
| 내 자동화 | 내가 만든 자동화 카드 목록 + 실행/수정/예약 |
| 확인할 일 | 기존 `humanTasks` 필터 뷰 (사람 확인 인박스) |
| 실행 기록 | 기존 `runTrace`의 간소 모드 (내 자동화의 실행만) |

### 5.2 관리 콘솔 (운영자/관리자/보안 — 현행 유지)

현행 18개 뷰 콘솔은 그대로 두되, 역할 기반으로 내비를 필터링한다. 업무 사용자에게는 만들기 콘솔 4항목만, 운영자 이상에게는 현행 그룹이 보인다. 상단에 모드 전환("관리 콘솔 열기")을 권한 보유자에게만 노출.

- 구현: `NAV_GROUPS`(`router.ts:29`)를 역할 조건부로 필터. 기존 `useCan`/`useRoles` 인프라 재사용.
- `myWork`의 "지금 확인이 필요합니다" 큐는 만들기 홈 상단의 컴팩트 스트립으로 흡수(확인할 일이 있을 때만 표시).

## 6. 화면 설계

### 6.1 만들기 홈 (`#create`)

구성 (위→아래):

1. **확인 필요 스트립** — 내게 배정된 사람 확인이 있을 때만. `MyWork`의 큐 로직 재사용 (`web/src/views/MyWork.tsx:37-61`).
2. **중앙 큰 입력** — "어떤 업무를 자동화하고 싶으세요?" 플레이스홀더 + 예시 칩 3개(실 테넌트 데이터 기반: 최근 템플릿/자동화에서 유도, 없으면 기본 예시). 입력 즉시 위저드 시작.
3. **템플릿 갤러리** — 카드형. 각 카드: 사람 말 제목("하이웍스 새 결재 알림"), "이 자동화가 하는 일" 2줄, 필요한 준비(사이트/로그인 연결) 칩, [이대로 만들기]. 데이터는 기존 커넥터 카탈로그 템플릿 API 재사용 (`ConnectorCatalog.tsx:144-158`의 프리필 파라미터 그대로).
4. **내 자동화** — 카드 목록: 이름, 상태 배지, 최근 실행 결과, [실행] [수정]. `listScenarios` 재사용.

빈 상태: 템플릿도 자동화도 없으면 입력 하나만 크게. "무엇을 보여줄까"가 아니라 "무엇을 시킬까"의 화면.

### 6.2 원패스 위저드 (만들기 홈 안에서 진행)

새 컴포넌트 `web/src/components/easy-create/` (위저드 셸 + 단계 컴포넌트들). 화면 전환 없이 만들기 홈이 위저드 모드로 바뀐다 (`#create?draft=<임시id>`로 진행 상태 보존 — 새로고침/뒤로가기 복원).

**단계 1 — 말하기.** 자연어 입력. 기존 `PromptScenarioGenerator`의 생성 API 호출·프리필(`usePrefill`) 로직을 훅으로 추출해 재사용. 생성 요청은 기존과 동일한 파이프라인(게이트웨이 정책·검증 포함).

**단계 2 — 준비 확인 (자동, 필요할 때만 표시).** 생성 파이프라인의 대상 사이트 추론(저장 시점 target 추론, 기존 기능)을 활용해:

| 점검 | 준비됨이면 | 부족하면 (인라인 서브스텝) |
|---|---|---|
| 대상 사이트 | 칩으로 표시만 | "OO 사이트를 등록해야 해요" → 인라인 `SiteCreateForm` 재사용 |
| 로그인 연결(세션) | 표시만 | "로그인 연결이 필요해요" → 인라인 `CaptureGuide`/`OperatorWizard` 재사용 |
| 로그인 정보(SecretRef) | 이름만 표시 | 관리자에게 요청하는 CTA(값 입력·노출 없음) |

규칙: 모든 점검이 준비됨이면 이 단계는 **접힌 한 줄 요약**으로만 보인다(익숙한 사용자에게 단계 추가 금지). 판정 로직은 `ReadinessCard`의 `siteReadiness`(`run-scenario/ReadinessCard.tsx:132-160`)를 공유 유틸로 추출해 재사용. 확인 불가면 "확인 필요" — green으로 추정하지 않는다.

**단계 3 — 초안 미리보기.** 생성된 IR을 **사람 말 단계 카드**로 렌더. 새 컴포넌트 `StepCards` — IR 노드 종류별 한국어 문장 렌더러(navigate→"OO에 접속합니다", act→"OO를 클릭합니다/입력합니다", extract→"OO를 읽습니다", verify→"OO를 확인합니다", 반복/분기→"각 항목마다 반복합니다" 등). 문장을 만들 수 없는 노드는 종류 라벨+원문 표시(날조 금지).

- 수정은 말로: 카드 아래 "고치고 싶은 점을 말해 주세요" 입력 → 재생성 API. 카드 직접 편집(P2)보다 먼저.
- [고급 보기] 토글: 기존 `VisualFlowCanvas`(`ScenarioForm.tsx:331`에서만 사용 중) + IR JSON. 기본은 숨김.

**단계 4 — 테스트.** [한 번 실행해 보기] → 같은 화면에서 단계 카드에 실시간 상태 오버레이(대기/실행 중/성공/실패/스킵). 데이터는 기존 `getRun` + `listRunSteps` 폴링 (RunDetailPanel과 동일 소스). 새 공유 컴포넌트 `TestProgress` — 위저드와 집중 스튜디오가 같이 쓴다.

- 성공: "테스트 성공! N단계가 처리되었습니다." + [이대로 사용하기(운영 예약)] [실행 증거 보기(runTrace 딥링크)] [계속 고치기].
- 실패: 사람 말 원인 + **복구 CTA 우선**("로그인 연결을 다시 해 주세요" → 인라인 세션 등록 / "입력값을 고쳐 주세요" → 해당 필드 포커스). 기술 상세(에러 코드·스텝 트레이스)는 접힌 상세. 분류는 기존 `ERROR_CATALOG`의 `userMessage`/`operatorAction` 재사용.
- 사람 확인(suspended): "사람의 확인이 필요해요" + 그 자리에서 처리(기존 human task 처리 컴포넌트 재사용) 또는 확인할 일로 연결.

### 6.3 집중 스튜디오 (기존 자동화 수정)

`#create?edit=<scenario_id>` — 만들기 홈에서 [수정] 진입 시 풀스크린 모드:

- 상단 바: 자동화 이름(인라인 편집), 초안/운영 배지, [저장] [테스트] [나가기].
- 좌/중앙: `StepCards`(6.2와 동일 컴포넌트).
- 우측 레일: 말로 고치기 입력, 준비 확인 요약(접힘), 최근 테스트 결과.
- 하단: `TestProgress` (테스트 중일 때).

기존 `ScenariosView`의 수동 폼·`ScenarioForm` 모달·승격 인박스는 관리 콘솔의 `scenarioStudio`에 남긴다(전문가 경로 유지). 업무 사용자용 수정은 집중 스튜디오로 일원화.

### 6.4 쉬운 언어 사전

새 모듈 `web/src/i18n/easy-labels.ts` — 만들기 콘솔 전용 용어 사전. 관리 콘솔 라벨은 불변.

| 내부 개념 | 만들기 콘솔 표기 | 금지 |
|---|---|---|
| 사이트 등록 | 업무 사이트 등록 | — |
| 세션 캡처 | 로그인 연결 (운영자 PC 등록) | "크리덴셜", "세션 캡처" |
| SecretRef | 로그인 정보 (이름만 표시) | 값·토큰 노출 |
| 시나리오 | 자동화 | "IR", "시나리오 버전" |
| 실행/run | 실행 | "run", 상태 enum 원문 |
| 증빙/artifact | 실행 증거 | "아티팩트" |
| 검증/validation | 자동 점검 | "V1–V11", 에러 코드 원문(상세 제외) |

상태 어휘는 기존 계약 어휘 유지: 준비됨/확인 필요/보류/차단, 취소됨. "확인 필요"를 green으로 바꾸지 않는다.

### 6.5 전역 "새로 만들기" (선행 설계 W1 계승)

관리 콘솔 톱바에 [새로 만들기] 버튼(선행 설계안 유지) — 항목의 최상단은 "자동화 만들기 → `#create`". 만들기 콘솔에서는 홈 자체가 만들기이므로 불필요.

## 8. 지켜야 할 불변식 (재설계에서도 불변)

1. **조용한 green 금지** — 확인 불가한 준비 상태는 "확인 필요". 쉬운 말로 바꿔도 상태 의미를 낙관 쪽으로 왜곡하지 않는다.
2. **SecretRef 비노출** — 로그인 정보는 이름만. 값·토큰·자격 URL·raw 프롬프트·raw 감사 본문 렌더 금지.
3. **RBAC 백엔드 권위** — 만들기 콘솔의 단순함은 표시 필터일 뿐, 인가 계층이 아니다.
4. **세션 = 운영자 PC 등록** 프레이밍 유지. 자격 수집으로 읽히는 문구 금지.
5. **생성 IR 검증** — 위저드가 만드는 모든 IR은 기존과 동일하게 codegen ajv + V1–V13을 통과해야 저장된다. 쉬운 미리보기는 검증의 대체가 아니다.
6. **어휘 정합** — abort→취소됨 체인 등 계약 어휘는 사전(6.4)을 거쳐도 의미 보존.

## 10. 성공 기준 (측정 가능)

1. 처음 쓰는 업무 사용자가 **안내 없이** 자연어 입력→테스트 성공까지 도달 (파일럿 재테스트로 검증).
2. 제작 완료까지 화면 이동 횟수: 현행 3~5회(스튜디오→보안→스튜디오→실행기록) → **0회** (모두 인라인).
3. 업무 사용자에게 보이는 내비 항목: 18개 → **4개**.
4. 준비물 부족 시 사용자가 받는 것: 차단 오류 → **그 자리 해결 CTA**.
5. 테스트 실패 시 첫 표시: 에러 코드 → **사람 말 원인 + 복구 버튼**.

## 12. 최종 설계 입장

지금의 콘솔은 "모든 기능이 보이는 하나의 콘솔"이었고, 그것이 업무 사용자에게는 학습 부담이었다. 재설계의 축은 기능 추가가 아니라 **밀도 분리**다: 업무 사용자에게는 말로 시작해 한 화면에서 끝나는 원패스를, 운영자/관리자/보안에게는 지금의 밀도 있는 콘솔을 준다. 쉬움은 숨김으로 만들되, 상태의 정직함(준비됨/확인 필요/차단)은 어떤 밀도에서도 같아야 한다.
